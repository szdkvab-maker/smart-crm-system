# Архитектура SmartCRM

## ADR-001 Выбор архитектуры

Статус: принято для учебного MVP. Python и SQL знакомы разработчику, срок первой
версии — три дня. Выбран монолит Django 5.2 LTS с серверными HTML-шаблонами и
локальными CSS-стилями. Отдельные React-приложение и API пока не нужны.
SQLite не требует настройки сервера; при многопользовательском развёртывании
следует рассмотреть PostgreSQL и повторить тестирование.

Браузер → URL-маршрут → авторизация → view/form → Django ORM → SQLite.
Ответ формируется HTML-шаблоном. Файлы стилей не требуют внешнего CDN.

## База данных

| Таблица | Назначение | Связи |
|---|---|---|
| User | Учётная запись Django | Один ко многим с Client, Deal, Task |
| Client | Имя, компания, контакты, заметки | owner → User |
| Deal | Название, сумма в KZT, статус, дата закрытия | owner → User; client → Client |
| Task | Название, описание, срок, приоритет, выполнение | owner → User; необязательный client → Client |
| ClientPortalProfile | Связь учётной записи клиента с CRM-карточкой | user → User; client → Client |
| RegistrationRequest | Заявка на регистрацию клиента | user → User; reviewed_by → User |
| PortalRequest | Заявка клиента на сделку или задачу | requester → User; результат → Deal или Task |

При удалении клиента удаляются его сделки; задачи сохраняются без клиента.
Перед удалением интерфейс предупреждает об этом. Суммы хранятся как Decimal,
отрицательные суммы отклоняются формой.

## Доступ и ограничения

CRM-пользователи работают с собственными записями и видят только их. Клиентские
учётные записи отделены профилем ClientPortalProfile: публичная регистрация создаёт
неактивную учётную запись и заявку, доступ появляется только после одобрения
пользователем с правом staff. Одобрение регистрации создаёт CRM-карточку клиента.
Клиент может видеть свои заявки и отправлять запросы на сделку или задачу; реальные
записи создаются только при одобрении. Клиентские учётные записи не могут вызывать
маршруты CRM или очередь согласования напрямую. Одобрение и создание записи
выполняются атомарно через /management/requests/. Общего пространства компании,
назначения задач коллегам и ролей менеджер/руководитель пока нет.

Все изменения выполняются POST-запросами с CSRF-защитой. Формы скрывают owner,
сервер назначает его из сессии. Клиенты в формах сделок и задач ограничены владельцем.

Локальный DEBUG включён. Перед публикацией обязательны собственный SECRET_KEY,
DEBUG=0, ALLOWED_HOSTS, HTTPS, настройка cookies, сервер приложений, static files,
резервное копирование и проверка `manage.py check --deploy`.

## План дальнейшей работы

1. Проверить MVP на компьютере участника и согласовать функции с командой.
2. Добавить демонстрационные данные и подготовить показ преподавателю.
3. По согласованию отправить feature-ветку в GitHub и открыть Pull Request.
4. Дополнить учебные артефакты: backlog, WBS, оценки, RAID Log и отчёт.

Автоматический CI запускает тесты при push/PR после загрузки workflow в GitHub.
CD и публичное развёртывание не настроены. Это не полный комплект лабораторных.

## ADR-002 Карточки клиентов и изображения

Статус: реализовано в UI V2. У Client добавлены kind, photo, position, industry,
contact_person, website и city. Миграция 0002 не удаляет старые поля и записи;
старые клиенты получают тип person, который можно поменять вручную.

Pillow проверяет изображения; приложение принимает JPG/PNG/WebP до 5 МБ и
16 миллионов пикселей, исправляет EXIF-ориентацию, уменьшает до 1000×1000
с сохранением пропорций и перекодирует в JPEG без исходных метаданных.
Прозрачность логотипов заменяется белым фоном. Имя файла — случайный UUID.

MEDIA_ROOT локален. URL /clients/<id>/photo/ проверяет сессию и owner,
возвращает private, no-store и nosniff. Прямой публичной раздачи media нет.
Старые файлы после замены/удаления карточки пока остаются на диске: их очистка
требует отдельного решения. Для восстановления сохраняются база и media вместе.

HTML по-прежнему формируется Django. JavaScript добавляет переключение темы,
предпросмотр фото и модальную боковую панель. Без JavaScript ссылка открывает
полную страницу карточки. Ошибка загрузки панели показывает повтор и обычную ссылку.
Диалог поддерживает Escape, удержание фокуса средствами браузера и возврат фокуса.

Метрики строятся по текущим данным пользователя. Распределение статусов не является
исторической воронкой конверсии; сумма выигранных сделок не означает полученную оплату.
Проценты роста и история изменения статусов не вычисляются без событийной модели.

Проверки V2: 22 серверных теста, включая миграцию V1→V2 с сохранением связей,
обработку фото, права владельца, пагинацию и реальные показатели. Дополнительно
проверены сценарии браузера: hover, диалог, темы, формы, мобильные размеры 390/320
и prefers-reduced-motion. Это проверка Chromium, не полный аудит всех браузеров.
